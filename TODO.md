- **Android's shared Music folder takes music and playlist files only.** Since Android 11 an app may
  write its own songs to `Music/` by path with no permission, but the media provider refuses other
  types there (a `.part` file, a JSON index): `DiskShelf.work` keeps unfinished songs in the app's

- **Android's regex engine is ICU, not the JVM's.** It refuses a bare `}` that the JVM accepts: `LyricsFormats`' `\{agent:([^}]+)}` failed its class initialisation on a phone, and since that is an `Error`, not an `Exception`, opening the lyrics killed the app (Pass 24). - **Phones get the release APK** (`assembleRelease`, R8, debug-signed, package `app.valen`). The debug APK is debuggable and runs Compose unoptimised; it is for development only. A release install is a separate app from `app.valen.debug` (settings and playlists do not carry over).
- **The Spotify browser profile may run an extension.** On the owner's machine a 230 MB extension process ran beside the Web Player (likely Helium's bundled content blocker). `--disable-extensions` would save it but could change what a free account's Web Player does; not changed, untested signed in.
- Lyprio is a signed service and its address and key belong to whoever runs it (Metrolist ships them from CI secrets). Valen's builds now carry the same endpoint Metrolist publishes, read from the git-ignored `local.properties` at build time into both the desktop app (`LyprioBuild`) and the APK (`BuildConfig`); the environment and `lyprio.json` still win over it, and without any of them only LRCLIB answers. Checked live from the packaged desktop binary (a word-timed search, kept in the cache); Android's copy is only checked to be in the APK. The key is Metrolist's, so it can be rotated or rate-limited at any time.
- **Spotify's half of an artist page is untested live** (it needs the signed-in Web Player); the GraphQL paths are the ones Orpheon's artist screen reads, plus `relatedContent.featuringV2`/`discoveredOnV2` for playlists, which are read defensively (empty when absent).
- **Artists are matched across services by name only.** Two different artists with the same name on two services would be merged; Valen has no shared id to tell them apart (ISRCs are per song, not per artist).
- **NixOS desktop testers cannot use Spotify yet** (browser discovery/profile on NixOS); a Nix flake is planned by the owner.
- **Desktop media controls show repeat and shuffle as off** (`MprisService` reports constants); the app's own buttons are right. Wiring `LoopStatus`/`Shuffle` to the coordinator is a small follow-up.
- **The disk cache trusts the first complete copy.** A song kept at one quality stays at that quality until it is trimmed or dropped; changing the quality setting does not refetch kept songs.
- **Android's SoundCloud HLS streams are not kept** (segments are addressed per lookup); progressive SoundCloud and all YouTube Music songs are.
- **Astra parametric EQ backend:** filter types, Q, presets and JSON/AutoEQ parsing are implemented
  alongside the existing effects. No notebook controls or file picker expose them yet; output profile
  selection is manual through the coordinator, not tied to output-device changes. Android has only
  been checked in headless Chrome, not on a device. Desktop still restarts ffplay instead of Astra's
  native real-time crossfade; Spotify cannot be processed. A +boost preset may deliberately use a
  negative preamp for headroom, as in Astra.
- **Audio stall detection (resolved in Pass 19):** this ffplay's audio clock keeps moving after
  input runs out, so clock stillness was not reliable. A stall is now the audio queue at `aq=0KB`
  for `stallAfterMs`, and `NativePlayback` reopens the song where it was; the FIFO test passes.
- **Android sound effects are `SoundDsp` inside ExoPlayer** (Pass 19; the Web Audio page engine is no longer used by the app). Checked by `SoundDspTest` (tone within 0.3 dB of `responseDb`, limiter, reverb tail, echo timing, mono, 8D, cost) and on the emulator (the chain configures on every stream; Nightcore's speed and pitch apply). Not heard on a real phone. The reverb is a Freeverb network there, not the desktop's convolution room, so the two rooms sound alike but not identical.
- **SoundCloud copy-protected tracks.** Newer label releases are offered only as `cbc-`/`ctr-encrypted-hls` (DRM). Valen does not play them on either platform; search leaves them out so another service's copy is offered.
- **Desktop effects and volume restart the stream.** FFmpeg reads these at start-up, so settled changes re-open the stream at the same place (a gap). Volume drags are coalesced, not seamless. A truly live chain would need a different playback architecture.
- **rubberband is optional.** Without it (another distribution's FFmpeg) pitch is a resample evened with atempo — measured right by `FfmpegEffectsTest`, but grainier on large shifts.
- **The song menu on Android is unseen on a device.** Compiled and laid out at phone size on the desktop only: the system share sheet (`Intent.createChooser`), Keep screen on (`View.keepScreenOn` while the stage is shown), the sheet's drag-to-close with a real finger, and the back order (menu → sheet → Home → exit, with a sign-in page's back always first) are unverified there.
- **`drawGlassLight` fills its whole draw scope with its sheen.** Inside `GlassSurface` that scope is the clipped shape; called anywhere else (the menu's opening drop) it must be clipped to its outline, or it washes the whole area faintly. Seen as a ghost of the full panel in the first frames of the menu's pour.
- Songs can be added only to lists of your own: a read list's next refresh and a mix's next remake replace their songs. The menu offers neither as a target.
- **Spotify needs its page focused to load media.** With the Chrome window in the background, the Web Player answers the play command and then never fetches audio: media element `paused=true`, `readyState=0`, `networkState=2`, no `audio-*.scdn.co` or licence request, and a stall/reload loop every ~30 s. `Page.bringToFront` alone was not enough while the window stayed unfocused; the desktop host now sends `Emulation.setFocusEmulationEnabled {enabled:true}` at connect and on every `activate()`, which makes `document.hasFocus()` true without stealing the user's window. Android's WebView has no such CDP switch: backgrounded WebView playback is unverified.
- The Web Player's own `setVolume` answers only once the player runs: 30 s on an idle page, 0 ms while playing. A play that waited for it started 30 s late (or never, behind the 20 s bridge timeout), so the adapter now asks with a 0.7 s cap (`SpotifyPlayer.setVolumeQuickly`) and never twice in a row; the page applies the level to its own player at once anyway.
- The MPRIS `Seeked` signal must be declared inside the interface (`MprisPlayer.Seeked`), not built by hand: dbus-java 5.x marshals a hand-built `DBusSignal` into a message the daemon rejects, and it answers by dropping the whole connection — one `playerctl position` took `org.mpris.MediaPlayer2.valen` off the bus until the next start.
- `PlayerSnapshot.canSkip` is now `true` for Spotify: skipping is the queue's job (the adapter plays a one-song context), and the transport buttons and MPRIS `CanGoNext` read this flag — `false` made `next` dead on the desktop.
- Signed-out SoundCloud label tracks are 30 s previews (service policy, played as such). The old page adapter refused streaming-only (HLS) tracks; the native resolver hands FFmpeg the HLS URL, so they play.
- YTM search parser read only one section of the live WEB_REMIX answer; widened to shelves, item sections and the top-result card (verified anonymously, 11 songs for "daft punk").
- Core queue/settings unit tests: `:core:jvmTest` green (11 tests), including recording dedupe.
- Spotify free-account refusals: show exact reason, no alternative invented.
- Google WebView sign-in may be refused: signed-out YTM still plays.
- Desktop Chrome defers media in a background tab. This only concerns the page-based adapters (Android's WebView, and Spotify's player): YTM/SC on the desktop no longer use a page at all. Spotify needs `Emulation.setFocusEmulationEnabled` (see above).
- YTM's web app can report `getPlayerState() == -1` while its `<video>` is already audible after an in-app song change; the page script now takes the element as the last word on playing state (fixes the queue stalling after `next`).
- YTM autoplay can replace the asked song with a different upload of the same title; the adapter keeps the asked video id and waits for it.
- A service often returns the same recording twice (album + single upload); search answers are collapsed by title and artist (`distinctRecordings()`); hand-built queues are left alone.
- On Android, Spotify "connected" is a heuristic (player page loaded, not a login page); a logged-out landing page can read as connected.
- Search at app start can beat the Spotify Web Player: the adapter waits up to 8 s for `api.ready`, then reports "still starting" beside the other services' results instead of failing the whole search.
- Screenshot capture renders offscreen with a 5 s settle; a shorter settle produced half-loaded artwork.
- Do not `pkill -f` a pattern that matches the shell's own command line (it killed the session); kill via a `/proc` PID scan instead.
- Packaged runtimes are trimmed by jpackage: `jdk.security.auth` must be listed or MPRIS reports `No session bus: com/sun/security/auth/module/UnixSystem`, and `java.net.http` must be listed or the Chrome probe dies with `NoClassDefFoundError: java/net/http/HttpClient` while Chrome is actually listening (`app-desktop/build.gradle.kts` now adds both; verified in the built `release` file).
- A packaged install does not ship Chrome: it needs a system Chrome/Chromium or `VALEN_CHROME_BIN`. Only documented, not a package dependency — without one the window opens and the services say they are unavailable.
- Chrome singleton hand-off: a second Chrome on the same profile prints "Opening in existing browser session" and exits, so `awaitReady` probes once more after the child exits before calling it a failure. Two Valen instances also share the profile and port; the second cannot take the MPRIS name (`Failed to register bus name`) and its `next` may drive the first one's Chrome — always test one instance.
- "Is this browser headless?" cannot be asked of `/json/version`: the headless engine is launched with an ordinary Chrome user agent (the Web Player refuses a headless one), so `HeadlessChrome` never appears and every Connect took a visible browser for already-visible and did nothing, silently. `ChromeLauncher` reads the process instead (`--remote-debugging-port=9333`, no `--type=`), and a sign-in stops a headless browser even when a killed earlier run started it (a SIGTERM'd Valen never calls `close()`, so its Chrome is the one the next run inherits). `ensureVisible()` returns false with the reason and the sign-in publishes it.
- The user agent must come from the engine, never the brand: a packaged install finds whatever Chromium
  the machine has, here Helium, whose `--version` is "Helium 0.21.3.1 (Chromium 157.0.8103.78)". Parsing
  the first four-part number gave 0.21.3.1, so Spotify saw `Chrome/0.0.0.0` and served "Unsupported
  browser"; the player never loaded, `player services not found` was the only symptom in the log, and
  every bridge call timed out behind it. `ChromeLauncher.engineMajor` takes the `Chrome`/`Chromium`
  number (or the plausible engine fallback), and the UA is passed in a window too, because the Web
  Player refuses brand browsers by name. Spotify audio is Widevine-protected: a browser without it can
  load the page and will never play.
- The user agent cache must hold the whole string. `cachedUserAgent` was filled from the second half of the concatenation (an `also` on the tail), so the first launch of a run announced a normal Chrome and every launch after it announced `Chrome/157.0.0.0 Safari/537.36` with no Mozilla prefix — and since a sign-in always replaces the browser, the broken one was exactly the launch a login depended on. `ChromeLauncherTest` now calls `userAgent` twice and compares the full line.
- A CDP host's closed state and its waiter map live under one lock. Cleared separately, a command could register between the clear and the socket close and then wait the full 30 s for an answer that could not come (the "Connect hangs" shape); and the timeout uses `withTimeoutOrNull`, so only the send's own expiry becomes "the browser did not answer" while a caller's cancellation stays a cancellation.
- A replaced adapter's collectors are cancelled explicitly: a `StateFlow` never completes, so without that a closed page kept writing its session and its old song into the wrapper's state, over the new page's.
- The volume/quality a rebuilt page is given are restored under the same lock a later slider move takes, and the value is re-read inside it; a detached restore could otherwise finish after a newer move and put the older level back.
- A native provider resolves the next song before the current ffplay process stops, so the sink still reports the old song for that window. `NativePlayback` ignores sink states while `play` is resolving (and applies the first real one when it returns); without that, a new song appeared at the old song's position for the length of the resolve.
- XTEST clicks do not follow a tiled column: XWayland reports the window at (0,0) whatever niri shows, so a synthetic click at a column's screen position lands on whatever X window the server thinks is there. Make the target fullscreen before clicking it (or use a real pointer); hover feedback on a screenshot is not proof the click will arrive.
- YouTube stream extraction without a browser: a plain InnerTube `player` call (IOS / ANDROID_VR clients) returns working URLs, but googlevideo serves only the first ~1 MB of them until the client's `n` challenge is solved — `bytes=0-` answers 403, which is exactly what mpv and ffmpeg ask for. NewPipeExtractor (`v0.27.1`, JitPack, GPL-3.0) solves it: its URLs answer 206 for `bytes=0-` and for mid-file ranges, and ffplay and mpv both play and seek them.
- SoundCloud without a browser: the API's `client_id` is scraped from the `"hydratable":"apiClient"` block of `soundcloud.com` (the page returns it to a plain HTTP client with a browser UA), cached for 45 minutes and re-read once on 401/403. Nothing is hardcoded.
- `ffplay` needs no `-nostdin` (that is an ffmpeg/ffprobe option): with it the process exits at once with "Failed to set value '-nostdin'". Its stderr is now kept and surfaced, which is how the mistake was found.
- Pause is SIGSTOP/SIGCONT on the `ffplay` process (the position therefore freezes exactly); seek restarts the process at the offset; the process exiting 0 is the end of the song. A shutdown hook kills the process so a stopped Valen leaves no audio running.
- `packageAppImage` is a directory, not a file: Compose asks jpackage for `--type app-image`. `scripts/appimage.sh` is the extra step and parses `packageVersion` from the build file.
- `--screenshot --play …` really plays the song through `ffplay` for the settle time. A scratch `XDG_CONFIG_HOME` whose `valen/settings.json` says `"volume": 0.0` keeps it silent (`ffplay -volume 0`; the coordinator sets the level before `play`) and keeps the run from rewriting the user's `lastProvider`.
- `Paint.asFrameworkPaint()` is deprecated in Compose 1.12 and the build treats it as an error: the desktop accessor is `skiaPaint`, Android's is `nativePaint`. The wash needs the native paint to turn dithering on (a dark gradient across a window bands without it), so `Paint.dither()` is an `expect/actual` in `ui/components`.- The artwork accent used to pick the single most common 12-bit colour bucket, which a gradient cover always loses (its colour is spread over many buckets) to any flat grey patch: a teal-to-purple cover came out brown-grey. It now groups pixels into 18 hue bins weighted by saturation and brightness, and falls back to the average grey under 6% coloured pixels.
- Playlists are Valen's own data, not an account's. `PlaylistLibrary` keeps `$XDG_DATA_HOME/valen/playlists.json` (`filesDir` on Android), every change under one `Mutex` that re-reads state inside it and persists after each change; an unreadable file is an empty library, never a crash. Re-importing a source playlist replaces it in place via `PlaylistSource.key`, so the short link is canonicalised to the reader's id. Nothing is written back to Spotify/YT/SC.
- An imported playlist mixes services on purpose: a track already on a service Valen can play is kept exactly (id, artwork, duration), and only unplayable entries are matched elsewhere. The matcher follows Mochy's importer (normalised title/artist, duration, version words) but is stricter: a version mismatch (remix/live/acoustic) scores 0, an unknown artist scores 0, and a live-album pairing is capped below the acceptance floor, so the wrong song is never substituted. An entry nothing matches is kept as `UnmatchedEntry` and shown under the playlist.
- Import matching runs one song at a time on purpose (a provider's search is rate-limited, and parallel searches produced more timeouts than answers). A search failure becomes an empty answer; a `CancellationException` is rethrown, so leaving the screen cancels the job instead of being logged as "not found".
- Account playlist reading uses the browser session the service's page already holds (`CdpHost.cookieHeader` / `DesktopHosts.cookiesFor`), not a new tab: YouTube Music and SoundCloud must never launch a browser for browsing, and on desktop they have no page. If Chrome is not running, the cookie read returns null (signed out) and the import screen offers the sign-in path — it does not start the browser.
- `ReadPlaylist.blocked` carries entries the service itself cannot play (regional/label blocks); the importer matches those elsewhere instead of keeping a track that would refuse to play.
- Android has no `PlaylistCatalog` for YouTube Music or SoundCloud: those adapters are page adapters. The import screen there offers pasted links only, until a native catalog exists.
- The coordinator publishes its snapshot from a 250 ms **real-time** poll, which `mainClock.advanceTimeBy` (virtual) cannot move. `ShellSmokeTest` asserted straight after `settle()` and read `null` on a loaded machine; the test now uses `settleUntil { … }`, which advances frames and waits real time for the condition.
- Compose UI tests cannot use `waitForIdle` here: the playing bars and the stage wash animate forever. `ShellSmokeTest` turns `mainClock.autoAdvance` off and steps time by hand.
- A full-screen phone sheet does not remove the screen under it from the semantics tree; a test (or a screen reader) finds both "Up next" nodes.
- Tiling XWayland geometry: a tiling compositor (niri, sway, Hyprland) resizes the frame but XWayland leaves AWT's content window at the size it was created with, so Compose draws a 1440×900 strip in the corner of a larger window. The two `-D` properties from the upstream report are not enough on their own; AWT's non-reparenting switch (`_JAVA_AWT_WM_NONREPARENTING`, the private `sun.awt.X11.XWM.awtWMNonReparenting` field) is. Environment variables are fixed before `main`, so `Main.kt` sets the field by reflection when it detects a tiling compositor, and `app-desktop/build.gradle.kts` opens `java.desktop/sun.awt.X11` in `jvmArgs` (so the packaged launcher has it too). Verified by X geometry: frame, `Content window` and `sun-awt-X11-XCanvasPeer` all follow a compositor resize.
- Layout width: `ContentColumn` used to stop at 1400dp and centre itself, which on a wide window looked like the app was drawn in a strip. Browsable screens now fill the width the panel leaves; only reading screens (Settings) pass `maxWidth`. Grids and the two big artworks scale with the window (Up next 1–6 columns, hero 248/312/360, stage cover up to 720).
- YouTube video results (not songs) use `hqdefault.jpg`, a 4:3 frame with black bars baked in, so those covers are letterboxed everywhere. Open; see HANDOFF §4.
- `ProcessHandle.Info.commandLine()` is not the browser's command line on this machine: for Helium it
  answers argv[0] alone (`arguments()` empty) while `/proc/<pid>/cmdline` has the whole line. Every
  check built on it saw no browser at all — `isHeadless()` reported "its window state could not be
  read" (the exact Connect error), `stopBrowser()` had nothing to stop, and a leaked headless engine
  could not be replaced. `ChromeLauncher.procCommandLine` reads `/proc` and is covered by a test.
- A sign-in's browser replacement is not a crash. The port is free for a few seconds while the
  headless engine becomes a windowed one, and `RetryingProvider`'s watchdog used to fire in the
  middle of a login: it closed the (soon stale anyway) adapter and published "Spotify's browser was
  closed". The watchdog now skips an adapter whose generation has moved, and `ChromeLauncher.starting`
  makes an in-flight start read as alive. `start()` and `stopBrowser()` also share a mutex: before,
  a play that reached for the browser during a sign-in's restart launched a second Chrome on the
  same profile, which handed off and exited.
- Spotify's sign-in state was guessed from the page ("no login button"): the Web Player's
  "Unsupported browser" page satisfies that and was read as connected, while every play timed out
  behind it. The state is now the `sp_dc` cookie (`Network.getCookies` on the tab's target, verified
  working without `Network.enable`), and `Disconnect` deletes the session cookies instead of only
  navigating to `accounts.spotify.com/logout` — the old sign-out left the browser signed in while
  claiming it had signed out.
- `CdpHost`/`CdpPageHost` had three ways to stall or drop work: no `onClosed`/`onClosing` handling
  (closing a host left `send()` callers waiting the full 30 s), an unchecked `ws.send` result, and a
  256-slot `MutableSharedFlow` fed by `tryEmit` that discarded bridge messages when the collector was
  busy (a discarded reply is a call timing out). Pending callers are now failed on close, a refused
  send fails immediately, timeouts carry the method name, and messages go through an unbounded
  channel behind the shared flow. One unparseable frame no longer kills the connection.
- The death watchdog re-checks the browser generation *inside* its lock, not only before the probe.
  A sign-in replaces the browser while the port is briefly free, so the probe can already have said
  "gone" when the generation moves; the pre-lock check saw the old value, closed the good adapter and
  published "Spotify's browser was closed" in the middle of a login. The lock now re-reads
  `generations.value` and leaves the adapter to `ready()`.
- A sign-in's `page.navigate(HOME)` that cannot be sent is the whole failure. YouTube Music and
  SoundCloud used to swallow it (`runCatching`), refresh a page whose socket was gone and start a
  poller that could never recover, so Connect looked dead; both now publish
  `SessionState.Unavailable` with the reason and return. (Not unit-tested: `CdpHost`/`CdpPageHost`
  constructors are private, so `SignInTabs` fakes cannot produce that failure.)
- A resolve failure while another stream is still running must stop that stream first. `ffplay` keeps
  ticking until it is stopped, and those ticks are published the moment `resolving` drops: they moved
  the failed song and could clear its reason. `NativePlayback` calls `player.stop()` before `failed()`
  and the failure stays the snapshot.
- The shared message flow exposes no `subscriptionCount` (that is on `MutableSharedFlow`; `shareIn`
  returns a `SharedFlow`), so the slow-subscriber test cannot poll for subscribers. Collectors are
  launched with `CoroutineStart.UNDISPATCHED`, which runs each one to its first suspension — after
  registration — inside the `launch` call, so both are subscribed before the first frame is
  delivered.
